## 已确认的隐患：异常退出后残留登录副本

真实下载进程中断并用原版程序重启、完成下载后，应用数据目录仍有 `.cookie-Owj7bn`（3,038 字节）和 `.download-info-tZTYXJ`（578,090 字节）。前者内容与本次传入的 YouTube Cookie 完全一致，后者保存解析结果和签名下载地址。正常析构会删除这些临时文件，但强制退出不会执行析构；原先启动路径没有相应清理。

这是应用私有数据目录内的残留，不是本轮发现了对外发送凭据。影响在于额外登录副本可以比所属任务活得更久，单纯删除保存的 Cookie 不会覆盖这类孤立文件。

修复范围限定为启动过程：取得应用数据目录独占锁之后，清理该目录第一层、符合应用临时文件命名规则的普通 `.cookie-*` 和 `.download-info-*` 文件；不递归、不跟随链接、不删除保存的凭据或任务检查点。独占锁必须在清理前取得，避免第二个实例破坏正在使用的临时文件。

修复后重新编译服务，再次对官方演示视频进行真实限速下载并强制退出。退出后实际生成 `.cookie-JIVASq`（3,038 字节）和 `.download-info-v7DaN1`（535,426 字节）；重启后这两个旧文件均不存在，保存的登录记录仍在，任务自动下载完成，67.779 秒成品通过全文件解码，完成后两类临时文件数量均为 0。证据保存在 `patched-recovery-result.json`。此修复会在下次启动时清理异常退出留下的文件，不意味着强制退出瞬间就能执行清理。

## 已确认的隐患：恢复时重新下载

原问题位置：`crates/core/src/download.rs` 的 `transfer_identity` 及 `transfer` 的来源目录选择。原先 `run_task` 恢复尚未完成媒体下载的任务时会再次解析，而 `transfer_identity` 将完整流 URL 纳入 SHA-256。

本轮暂停恢复时：原 `.part` 为 786,479 字节，恢复后创建了不同身份的来源目录，并记录 “The source or format changed; this attempt starts a new transfer and preserves the previous partial files.”。重启恢复测试也记录相同提示。

随后使用同一官方视频连续运行两次真实 yt-dlp 解析，视频 ID、格式 ID 18、尺寸、帧率、编码信息相同，但完整 URL 不同，变化的查询参数包括 `expire`、`sig`、`lsig`、`n`，以及 CDN 的 `id` 等字段。两次格式元数据均没有精确 `filesize`。因此，即便视频和格式没有改变，当前策略也会使恢复下载丢失已完成的传输进度。

影响：大视频或频繁暂停时会浪费带宽、恢复时间和临时空间；旧分片在任务暂停／失败期间可能保留，成功后会清理。本轮成功完成的演示任务已确认不再保留 sources 文件。

修复复用现有下载检查点，在开始传输前保存原解析结果，暂停和重启后直接使用原下载 URL 和分片目录。旧版已完成媒体下载的检查点仍兼容；未保存解析快照的旧任务首次恢复仍可能重新下载。视频／音频流明确返回 HTTP 401、403、404 或 410 时最多重新解析一次；取消、磁盘错误、字幕失败不会触发媒体重下。

保留完整来源身份规则，没有删除 URL 签名参数来跨地址拼接：同样的格式 ID 和尺寸不能证明两次响应字节相同，而本次连 CDN `id` 也发生变化。旧地址失效并且新来源身份改变时仍会隔离旧分片，优先保证成品正确。
